# 42_톰캣 클래스 패치

> 톰캣 클래스 패치 유의사항

## 1. 배경

Spring Framework를 톰캣으로 배포했을 경우 .class 파일만 교체해주는 것으로 클래스 패치가 가능하다.

굳이 전체를 재빌드할 필요 없이, 클래스 파일 교체만으로 원하는 부분의 수정이 가능한 것이다.

그런데 여기서 조심해야 할 것이 있다.

수정한 클래스 하나만 바꿔 끼우고 어플리케이션 재기동하면 되겠지라고 생각하기 쉬우나 서비스가 정상적으로 실행되지 않을 수도 있다.

<br>

## 2. 클래스 파일 교체 범위 판단 기준

그러면 언제 수정한 파일 하나만 바꾸면 되고, 언제는 연관된 다른 클래스까지 함께 바꿔줘야 하는가?

### 1) 핵심

**"컴파일 시점에 클래스 간 관계가 얼마나 확정되어 바이트 코드로 정해지는가"**

<br>

### 2) 수정한 해당 클래스 파일만 교체해도 되는 경우

- 메서드 시그니처(메서드 명, 파라미터의 타입의 순서 / 개수)의 변경 없이, 메서드의 내부 로직만 변경되는 경우
  - 단, 메서드 시그니처가 변경되더라도 수정한 해당 클래스 내에서만 호출되는 경우라면 해당 클래스만 교체해도 무방함. 그렇다고 해도 항상 사용처(usage)를 체크할 것!
- public static final 상수를 추가 및 수정했지만, 해당 클래스 내에서만 사용하는 경우

<br>

### 3) 연관된 클래스 파일까지 전부 교체해줘야 하는 경우

- 메서드 시그니처의 변경
- public static final 상수 값 변경
- 클래스 계층 구조 변경 (상속, 인터페이스)
- public / protected 필드 추가 및 삭제

위의 4가지 중 하나라도 변경이 되었고, 그것을 다른 연관된 클래스에서 참조하고 있는 경우 연관된 클래스들까지 전부 교체해줘야 한다.

물론, 위의 4가지 변경 사항에 대해서는 참조하고 있는 클래스의 소스 코드 자체도 변경이 필요하기 때문에 (변경하지 않을 경우 컴파일 에러 발생 가능성) 엄밀히 말하면 수정된 클래스에 포함되지만, 그렇지 않은 경우도 있다.

#### (1) public static final 상수 값 변경

이 케이스에서 주목할 것은 상수의 '값' 변경이다.

자바 컴파일러는 컴파일 시 상수 필드를 참조로 남기지 않고, 바이트 코드로 변환할 때 값으로 치환하여 넣는다.

```java
public class A {
    public static final int MAX_RETRY = 3;
}

public class B {
    void doSomething() {
        int retry = A.MAX_RETRY;  // 컴파일 시 3으로 치환됨
    }
}
```

즉, 여기서 만약에 A 클래스의 MAX_RETRY 값을 5로 수정한 다음 컴파일을 하면 B 클래스의 retry 필드의 값은 5가 되는 것이다.

따라서 A 클래스를 수정했다고 해서 A 클래스만 변경하게 되면 B 클래스에는 변경 사항이 반영되지 않는 이슈가 발생한다.

<br>

## 3. JVM 클래스 로딩 원리

JVM은 핫로드 기능이 없다. 이미 클래스 로더가 최초 실행 시 로딩한 클래스 파일들만 계속 사용한다.

따라서 클래스 파일을 선 변경하고 후 재기동을 해도 무방한게, 어차피 물리적인 파일을 교체해도 클래스 로더가 가지고 있는 클래스 파일은 교체 이전의 파일을 메모리에 적재한 파일이기 때문에 상관없다.

결론적으로 매우 당연하지만 수정한 클래스 파일만 교체하는 핫패치를 해서 내용을 적용하기 위해서는 어플리케이션의 재시작이 필요하다.
